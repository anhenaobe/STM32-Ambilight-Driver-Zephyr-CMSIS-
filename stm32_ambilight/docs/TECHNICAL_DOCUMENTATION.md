# Technical Documentation

## Scope and status

This repository implements an Ambilight-style controller for a 120-LED SK6812 RGBW strip. A host PC sends Adalight RGBW frames over UART; the STM32 validates each frame and creates the timed signal required by the LEDs.

Two STM32L432KC firmware implementations are present:

| Implementation | Directory | Current status |
| --- | --- | --- |
| CMSIS | `cmsis_platformio/` | Functional, stable reference implementation. |
| Zephyr | `zephyr_platformio/` | Development implementation that requires further debugging and hardware validation. |

The implementations have a similar intended data path, but this repository does not claim that the Zephyr path currently behaves like the CMSIS path.

## Architecture

```mermaid
flowchart LR
    HOST["Host PC"] -->|"Adalight RGBW over UART"| PARSER["STM32 frame parser"]
    PARSER --> RGBW["RGBW color buffer"]
    RGBW --> PWM["RGBW-to-PWM translator"]
    PWM --> DMA["DMA"]
    DMA --> TIM2["TIM2_CH2 / PB3"]
    TIM2 --> STRIP["SK6812 RGBW strip"]
```

The host decides the visual content. Firmware receives already ordered color bytes, validates their frame, translates each bit to a PWM duty-cycle sample, and transfers those samples through DMA to `TIM2->CCR2`.

## Protocol and data path

The firmware expects an Adalight frame:

```text
Ada + high LED-count byte + low LED-count byte + checksum + RGBW payload
```

The LED count is 120 and the payload uses four bytes per LED, for 480 payload bytes. The parser checks the `Ada` header, the count/checksum fields, and the expected payload length. A valid payload is converted into PWM samples; the timer output on `PB3 / TIM2_CH2` drives the strip data input.

UART, the Adalight parser, the RGBW buffer, the PWM buffer, DMA, and the timer are distinct responsibilities. The LED waveform itself is generated by the timer/DMA path, not by UART.

## Firmware implementations

### CMSIS

The CMSIS firmware uses register-level peripheral control. It is organized into `src/APP/` (parsing and translation), `src/BSP/` (UART, DMA, and PWM/timer setup), and `src/main.c` (initialization and coordination). Its PlatformIO configuration declares the `nucleo_l432kc` board and the CMSIS framework. This is the implementation considered functional and stable for this repository.

### Zephyr

The Zephyr firmware uses Zephyr configuration, DeviceTree, and driver interfaces while retaining application and BSP-style directories. Its main PlatformIO environment and diagnostic environments are declared in `zephyr_platformio/platformio.ini`; relevant Zephyr files are in `zephyr_platformio/zephyr/`.

It is retained for development and diagnosis. Do not use its presence as evidence of an equivalent, working firmware path.

## Host-side tools

`host/` contains Python senders and screen-capture utilities. The modular entry point is `adalight_stable_rgbw.py`, and its configuration is in `adalight_stable_rgbw/config.py`. The configured serial port, capture device, display index, and visual calibration values are local-machine settings; they must be reviewed before use on another computer.

The source currently imports `numpy`, `mss`, and `pyserial`. It can also use `dxcam` when selected as the capture backend. The repository does not currently provide a locked dependency file or a hardware-independent host run procedure.

## Hardware and safety

The LED strip uses an external 5 V supply. Do not power the strip from the STM32 board. The STM32 ground, the LED-strip ground, and the power-supply ground must be common, and the data line should pass through the documented 300 ohm series resistor. See [`hardware/WIRING.md`](../hardware/WIRING.md) for the complete connection checklist.

## Validation boundary

Only commands declared by the repository's PlatformIO configurations are documented as build entry points. Hardware output, serial-port assignment, power delivery, and LED behavior require the actual connected system; they are not inferred from a source-only build.
